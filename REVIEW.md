# REVIEW.md

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (`app/main.py:33-37`) | Uses `punch_in.replace(hour=h, minute=m, ...)` directly on a UTC timestamp without converting to IST or accounting for attendance date. | A punch-in at 09:35 IST (04:05 UTC) produces incorrect late minutes because replacing UTC hour `4` with shift start hour `9` compares against `09:30 UTC` instead of `09:30 IST`. | Converted punch-in instant to IST (`UTC+05:30`), constructed shift start datetime on the IST attendance date, checked `diff_sec > 600`, and calculated `diff_sec // 60`. |
| 2 | `compute_work_hours` (`app/main.py:40-41`) | Uses standard Python `round(..., 2)` which performs Banker's Rounding (round half to even). Rule R4 requires half-up rounding. | A work duration resulting in `8.125 hours` rounds to `8.12` instead of `8.13`. | Replaced float `round()` with exact `Decimal` quantization using `ROUND_HALF_UP`. |
| 3 | `compute_overtime` (`app/main.py:44-47`) | Shift end date is calculated assuming the same calendar day as `date_str`, ignoring overnight shifts. It also returns positive overtime even when duration is under 30 minutes (violating R3). | For an overnight shift (22:00 - 06:00), punch-out at 06:40 IST compares against 06:00 IST of the previous day (~24h overtime). Also, 15 minutes overtime returned 15 instead of 0. | Added overnight shift detection (`shift_end <= shift_start`), set `shift_end_date` to next day for overnight shifts, and enforced the `>= 30 minutes` threshold (returning 0 if `< 1800` seconds). |
| 4 | `POST /employees` (`app/main.py:77-85`) | Uses check-then-insert (`find_one`) subject to race conditions. Does not validate `shift_start != shift_end`. Does not format `created_at` as epoch milliseconds. | Concurrent identical requests create duplicate employees or return 500 error instead of 409. Creating an employee with `shift_start == shift_end` succeeds. | Enforced database unique index on `emp_code`, caught `DuplicateKeyError` to return 409, added validator checking `shift_start != shift_end`, and formatted `created_at` to epoch milliseconds. |
| 5 | `GET /employees` (`app/main.py:88-96`) | `skip` is `page * page_size` (skipping page 1), `total` counts the whole collection ignoring department filter, and results are not sorted by `emp_code` ascending. | Page 1 returns items 21-40 instead of 1-20. When filtering by department, `total` reflects all employees. Result order is non-deterministic. | Fixed skip to `(page - 1) * page_size`, passed query filter `q` to `count_documents(q)`, and added `.sort("emp_code", 1)` to MongoDB cursor. |
| 6 | `POST /attendance/punch-in` (`app/main.py:99-121`) | Uses check-then-insert `find_one` allowing race conditions. Crashes with 500 TypeError when `emp` is not found. Accepts invalid statuses (e.g. `ABSENT`). Adds non-standard `id` field. | Two concurrent punch-in requests both insert documents. Punching in for non-existent `EMP9999` returns 500 error. Response contains `id` property instead of OpenAPI schema. | Used compound unique index `("emp_code", "date")` catching `DuplicateKeyError` for 409 Conflict. Checked `emp` existence for 404. Restricted status enum to `PRESENT`, `WFH`, `ON_DUTY` (422 for others). Formatted response per OpenAPI schema. |
| 7 | `GET /attendance` (`app/main.py:124-150`) | Loads entire collection into Python memory with `list(db.attendance_logs.find(q))`, sorts in Python, and slices for pagination. Fails to validate `date_from > date_to`. | Extremely slow and causes OOM crash on 100k dataset. Querying `date_from="2026-07-10"` & `date_to="2026-07-01"` returns 200 instead of 422. | Moved sorting (`date` desc, `emp_code` asc), skip, and limit to MongoDB cursor level, passed `q` filter to `count_documents`, and added validation returning 422 if `date_from > date_to`. |

### Items examined and decided were NOT defects:
1. **Environment variable loading (`load_dotenv()`)**: Correctly allows local `.env` file configuration while letting real environment variables override them.
2. **MongoDB database client initialization**: Standard `MongoClient` setup reading `MONGO_URI` and `MONGO_DB` from environment variables.
